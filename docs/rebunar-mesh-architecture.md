# Rebunar Mesh — архитектура и план реализации

Статус: проектирование. Это не реализованный Bluetooth-клиент и не обещание доставки сообщений.

## Цель

Добавить к существующему интернет-мессенджеру Rebunar дополнительный канал связи между Android-устройствами поблизости. Интернет остаётся основным каналом. Bluetooth Mesh — необязательный резервный канал с принципом store-carry-forward: устройство может временно сохранить зашифрованный пакет и передать его дальше при встрече с другим участником сети.

## Текущее состояние репозитория

- Основной интерфейс — веб-приложение Vite в `frontend/`.
- Backend — Flask в `server.py`.
- В репозитории есть Matrix SDK и инфраструктура подключения Matrix/E2EE.
- Отдельный Android-проект, Kotlin-код и AndroidManifest.xml пока не обнаружены.
- Следовательно, полноценный BLE Mesh нельзя безопасно реализовать только внутри текущей веб-страницы. Нужен отдельный нативный Android-компонент/клиент и согласованный способ связи с аккаунтом Rebunar.

## Архитектура верхнего уровня

1. Интернет-канал: существующая серверная доставка сообщений Rebunar; он остаётся основным.
2. Локальный канал: Android BLE для обнаружения соседних устройств Rebunar и передачи небольших зашифрованных пакетов.
3. Перенос пакетов: ограниченная очередь store-carry-forward с TTL, лимитом размера, лимитом числа переходов и дедупликацией.
4. Синхронизация: при восстановлении интернета устройство сверяет очередь с сервером и удаляет подтверждённые пакеты.
5. Группы: отдельный этап после личных сообщений. Для групп необходимы управление членством, ротация ключей и обработка исключённых участников.

## Обязательные правила безопасности и приватности

- Mesh выключен по умолчанию; пользователь сам включает участие и может отключить его в любой момент.
- Не передавать контакты, телефон, аватар, имя пользователя, список чатов, файлы или содержимое локальной базы.
- В BLE-рекламе не размещать Rebunar user ID, username, постоянный device ID или текст сообщения.
- Для обнаружения использовать краткоживущие вращающиеся идентификаторы, не позволяющие легко отслеживать устройство.
- Содержимое пакета шифруется на устройстве отправителя для конечного получателя(ей). Промежуточный ретранслятор хранит и пересылает только ciphertext и минимальные метаданные маршрутизации.
- Аутентифицировать участников и проверять целостность каждого пакета; не доверять данным соседнего устройства.
- Ограничить срок хранения (TTL), число переходов, размер очереди и частоту приёма, чтобы снизить риск спама и DoS.
- Защищаться от повторной доставки, подмены, повреждённых и слишком больших пакетов.
- Не считать Bluetooth pairing единственной защитой: требуется криптографическая защита самого сообщения.
- Не включать автоматическую отправку файлов или вложений в первой версии.
- Не заявлять пользователю гарантированную доставку. Статусы должны различать «в очереди», «передано соседнему устройству», «доставлено получателю» и «истёк срок хранения».

## Android и совместимость

- Для Android 12+ требуются соответствующие Nearby Devices permissions: BLUETOOTH_SCAN, BLUETOOTH_ADVERTISE и/или BLUETOOTH_CONNECT — только по фактической необходимости и с объяснением пользователю.
- Для Android 11 и ниже BLE-сканирование требует legacy Bluetooth permissions и location permission по правилам соответствующей версии Android. Это важно для существующих Android 11 устройств.
- Фоновое сканирование и доставка ограничиваются энергосбережением и политиками Android/OEM. Нельзя обещать непрерывную работу в фоне.
- BLE advertisements подходят для обнаружения, а для полезной нагрузки потребуется отдельный защищённый канал передачи (например, GATT). Нужно учитывать ограничения MTU, пропускной способности и времени соединения.
- Реализовать сначала Android-only пилот. Веб-версия показывает состояние Mesh и очередь только после появления надёжного native bridge; не запрашивать Bluetooth-разрешения у веб-версии без реальной функции.

## Этапы

### Этап 0 — аудит и проектирование
- Зафиксировать текущую архитектуру и границы веб/сервер/Matrix.
- Определить модель угроз, формат пакета, криптографический протокол и правила согласия.
- Проверить лицензии и совместимость выбранных библиотек.

### Этап 1 — Android proof of concept
- Отдельное приложение/модуль Android на Kotlin.
- Явное включение Mesh и разрешения Android.
- Обнаружение двух тестовых устройств и передача тестового зашифрованного пакета.
- Никакого доступа к адресной книге и медиа.

### Этап 2 — приватный ретранслятор
- Store-carry-forward, TTL, hop limit, deduplication, ограничения очереди.
- Проверка подписи/целостности и end-to-end encryption.
- Тесты потери связи, повторов, подделанных и повреждённых пакетов.

### Этап 3 — интеграция с Rebunar
- Связать нативный компонент с авторизованным аккаунтом безопасным способом.
- Добавить понятные настройки, согласие, статусы и журнал диагностики без содержимого сообщений.
- Не менять существующие интернет-чаты и Matrix-подключение без отдельной проверки.

### Этап 4 — группы и полевые испытания
- Отдельно спроектировать групповые ключи и членство.
- Проверить реальную дальность, скорость, батарею, фоновые ограничения и доставку через несколько устройств.
- Публиковать ограничения явно; не обещать связь на большие расстояния без плотной цепочки участников.

## Критерии допуска к первой публичной версии

- Независимый обзор модели угроз и криптографической реализации.
- Тесты на Android 11 и Android 12+.
- Пользователь может полностью выключить Mesh и отозвать разрешения.
- Ретранслятор не может прочитать содержимое сообщений.
- Нет постоянного идентификатора пользователя в BLE-рекламе.
- Есть ограничения против спама, переполнения очереди и replay-атак.
- Успешные тесты с двумя и несколькими устройствами, включая потерю/восстановление интернета.
- Документированы ограничения фоновой работы и доставки.
