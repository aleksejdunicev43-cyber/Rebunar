# ADR: безопасная архитектура сквозного шифрования личных чатов

- Статус: предварительное решение; production-внедрение заблокировано до проверки транспорта и модели устройств.
- Дата: 2026-11-04.
- Область: только личные чаты Rebunar 1:1. «Избранное»/личные заметки, сообщества, публикации и вложения не входят в первый этап.

## Цель

Текст личного сообщения должен шифроваться на устройстве отправителя до отправки в сеть. Сервер Rebunar должен получать и хранить только ciphertext. Расшифровать сообщение могут только доверенные устройства участников диалога. Шифрование включается автоматически; отдельная ручная привязка Matrix пользователем не должна быть обязательной частью UX.

## Что подтверждено текущим кодом

- `frontend/features/messages/api.js` отправляет поле `text` в `POST /api/messages/send` и получает историю из `GET /api/messages/history`.
- `server.py` сохраняет личные сообщения в `messages.text` открытым текстом; endpoint истории возвращает это поле, а список чатов использует его как preview.
- Личные заметки используют ту же таблицу `messages`, но имеют `sender_id = receiver_id`; их нельзя смешивать с миграцией личных чатов.
- В проекте уже есть `matrix-js-sdk` и код `initRustCrypto()`, но он вызывается только после ручной Matrix SSO-привязки.
- Текущий Matrix homeserver в проверенном коде — `https://matrix.org`. Backend хранит только данные привязки Matrix. Обычные сообщения Rebunar сейчас через Matrix не отправляются.
- Android shell найден в ветке `feature/rebunar-android-shell` (workflow `.github/workflows/publish-android.yml` собирает APK из этой ветки). `MainActivity.kt` создаёт WebView и загружает `https://rebunar.pythonanywhere.com/new`; HTML/JS приложения приходит с сервера при запуске, а не из APK. В shell нет E2EE-native bridge, Android Keystore integration или bundled frontend assets. Поэтому локальная криптография только в удалённом JavaScript НЕ защищает от оператора/компрометации сервера, который может отдать изменённый JavaScript и перехватить текст до шифрования или после расшифровки. Это критический риск для заявленной модели угроз.
- `server.py` отдаёт `frontend/build/index.html` для `/new`, если production build существует; остальные собранные файлы обслуживаются через `/new/<path>`.
- `vite.config.js` задаёт base `/new/build/`, поэтому production HTML ссылается на хешированные JS/CSS-файлы под `/new/build/assets/`.
- `frontend/shared/api/client.js` использует относительный `API_BASE = '/api'` и `credentials: 'same-origin'`. Следовательно, Android не должен просто перенести HTML на `file://` или на отдельный origin без отдельного проектирования cookies, CORS и сессий.

## Оценка вариантов

### Не писать собственную криптографию

Не реализовывать самостоятельно X25519/Ed25519, Double Ratchet, prekeys, сериализацию криптографических состояний или собственный протокол обмена ключами. Простая обёртка AES-GCM не решает безопасную первичную установку ключей, проверку личности, защиту от повторов и смену устройств.

### Signal libsignal

Официальный репозиторий Signal содержит реализацию Signal Protocol и TypeScript API, но прямо указывает, что использование вне официальных клиентов не поддерживается, а API могут меняться без уведомления. Поэтому не принимать его как основу Rebunar без отдельного анализа лицензии, API, поддержки браузера/Android и последствий использования неподдерживаемой интеграции.

### Matrix Rust Crypto / matrix-js-sdk

Это наиболее зрелая уже присутствующая в проекте криптографическая основа: текущий frontend уже зависит от `matrix-js-sdk` и умеет инициализировать Rust Crypto. Matrix SDK автоматически шифрует/расшифровывает события и предоставляет модель устройств и проверки доверия. Однако это не означает, что текущая интеграция уже защищает чаты Rebunar: сейчас она не участвует в отправке и получении обычных сообщений.

Ограничение: Matrix — одновременно протокол, транспорт и экосистема серверов. Если использовать matrix.org, Rebunar будет зависеть от внешнего homeserver и его правил регистрации/доступности. Если запускать собственный homeserver, потребуется отдельная постоянно работающая инфраструктура, резервное копирование и сопровождение; текущий Flask/PythonAnywhere deployment сам по себе не является Matrix homeserver.

### Предварительное направление

Не начинать с E2EE в удалённом JavaScript: текущий Android APK загружает исполняемый код с PythonAnywhere при каждом запуске, поэтому сервер может подменить клиент. До криптографического spike сначала устранить этот разрыв доверия: Android должен запускать проверенный frontend, упакованный в подписанный APK (с безопасной процедурой обновлений), а не незаметно загружать произвольный JS с сервера. Для веб-версии отдельно описать ограничение модели угроз: если браузер каждый раз получает JS с того же сервера, оператор этого сервера теоретически может заменить клиентский код.

### Технический план локального Android frontend

1. CI должен собирать Vite frontend и включать весь результат `frontend/build/**` в APK assets. Сборка APK обязана завершаться ошибкой, если каталог пуст или отсутствует `index.html`.
2. Android WebView должен загружать HTML из APK, а не получать главный документ и исполняемые файлы с PythonAnywhere. Хешированные JS/CSS/chunks из `/new/build/**` должны отдаваться только из assets APK; отсутствие локального файла должно давать ошибку, а не незаметный сетевой fallback.
3. При этом страница должна сохранять доверенный origin `https://rebunar.pythonanywhere.com`: API-клиент использует относительный `/api` и same-origin cookies. Нельзя без проверки переносить страницу на `file://` или `appassets.androidplatform.net`, иначе изменятся origin, cookie и CORS semantics.
4. Рассмотреть AndroidX `WebViewAssetLoader` или строго ограниченный `shouldInterceptRequest` для локальных путей на принадлежащем Rebunar HTTPS-origin. Перехватывать только заранее зарезервированные пути frontend assets; `/api/**` оставить сетевым API-запросам. Не использовать широкое правило, которое может случайно подменить API-ответ локальным файлом.
5. Не разрешать произвольную загрузку исполняемых ресурсов с сервера. Помимо локальных JS/CSS, проверить динамические chunks, worker/service-worker, wasm, шрифты, favicon, изображения и любые runtime imports. Для неизвестного пути под frontend asset namespace — fail closed.
6. Внешние ссылки должны по-прежнему открываться вне WebView. Сетевые запросы API остаются HTTPS; TLS-ошибки не обходить. Не добавлять JavaScript bridge без отдельного threat review.
7. В CI проверить состав APK и наличие всех ссылок из собранного HTML/CSS/JS в assets. После сборки протестировать login/logout, сохранение сессии после перезапуска, отправку/получение сообщений, загрузку аватара и работу двух аккаунтов на Android 11.
8. Локальный bundle устраняет возможность незаметно подменить исполняемый frontend через обычный ответ PythonAnywhere в установленном APK, но не защищает от компрометации самого APK signing key, вредоносного обновления APK, ОС/устройства или браузерной версии. Обновление кода должно проходить через проверяемую подпись APK и управляемый release process.

Официальный Android `WebViewAssetLoader` предназначен для выдачи локальных ресурсов через HTTP(S)-URL внутри WebView и сохраняет совместимость с Same-Origin Policy; документация также предупреждает использовать для этого только собственные домены и зарезервированные пути. Это ориентир для реализации, а не утверждение, что интеграция уже выполнена.

После устранения разрыва доверия провести изолированный технический spike на текущем `matrix-js-sdk`/Rust Crypto в доверенном клиенте: два тестовых устройства, отдельная тестовая комната, проверка шифрования, offline-доставки, проверки ключей и восстановления сессии. Не менять production send/history endpoints и не переключать существующие чаты на этом этапе.

Параллельно выяснить, какая модель транспорта допустима для Rebunar:
1. matrix.org с автоматическим созданием/привязкой Matrix identities без ручного SSO;
2. собственный Matrix homeserver на отдельной поддерживаемой инфраструктуре;
3. иной проверенный E2EE SDK с поддерживаемой браузерной и Android-сборкой и понятной лицензией.

Не выбирать самописный криптографический протокол как обход этой задачи.

## Обязательные требования перед production

1. Приватные ключи и ratchet state никогда не отправляются на Flask backend и не попадают в логи/аналитику.
2. На сервере хранятся только ciphertext, необходимые routing-поля и ограниченная служебная метаинформация.
3. Обмен ключами аутентифицирован; пользователь может проверить собеседника через QR или safety number. Непроверенное устройство явно отмечается.
4. Новое устройство не получает доступ к старой истории автоматически без осознанного безопасного переноса/восстановления ключей.
5. Предусмотрены отзыв потерянного устройства, смена ключей и понятное восстановление доступа.
6. Нет незаметного downgrade: зашифрованный чат не принимает plaintext fallback. Сервер отвергает незашифрованные payloads на E2EE endpoint.
7. Существующие сообщения остаются legacy plaintext и маркируются как незашифрованные; нельзя задним числом объявлять их E2EE.
8. Список чатов не должен раскрывать preview открытого текста. Для новых сообщений preview формируется на клиенте либо заменяется нейтральной меткой.
9. Вложения, изображения, поиск по тексту, push previews, typing/read receipts и групповые чаты не включаются в первый этап, пока отдельно не спроектированы их утечки метаданных и шифрование.
10. Проверены Android 11 WebView/браузер, обновление приложения, очистка кэша, восстановление IndexedDB и работа двух разных аккаунтов/устройств.
11. Перед включением для пользователей — threat model, автоматические тесты протокола и независимый security review.

## Безопасная последовательность внедрения

1. Зафиксировать и протестировать текущее поведение обычных чатов и self-notes.
2. Убрать недоверенную загрузку исполняемого JS из Android shell: определить стратегию bundled frontend и проверяемых обновлений; отдельно оценить browser/PWA threat model.
3. Определить модель безопасного хранения ключей и восстановления для Android 11/WebView и браузера.
4. Выполнить изолированный E2EE spike на выбранном SDK и транспорте.
5. Спроектировать отдельные таблицы/эндпоинты для device keys, prekeys и encrypted envelopes; не переиспользовать `messages.text` как хранилище открытых E2EE payloads.
6. Добавить параллельный тестовый контур без изменения старых сообщений.
7. Пройти сценарии двух пользователей, offline delivery, новых/отозванных устройств, неверных ключей и сетевых ошибок.
8. Только после прохождения проверок переключать новые личные чаты. Существующую историю оставить доступной с явной пометкой «Не зашифровано».
9. Удалять Matrix-настройки и старый код только после успешной замены, если выбранная архитектура больше не использует Matrix.

## Текущий результат

Это архитектурная фиксация и план безопасного исследования, а не готовое E2EE. До завершения spike нельзя показывать пользователям значок «Сквозное шифрование активно» и нельзя заявлять, что сервер не может прочитать сообщения.
